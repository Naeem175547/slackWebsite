Option 1 — @BeforeInsert() / @BeforeUpdate() ⭐
For your case, this is the simplest approach.

import {
  Entity,
  PrimaryGeneratedColumn,
  Column,
  BeforeInsert,
  BeforeUpdate,
} from 'typeorm';

@Entity('users')
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ unique: true })
  email: string;

  @Column()
  password: string;

  @Column({ unique: true })
  username: string;

  @Column({ nullable: true })
  avatar: string;

  @BeforeInsert()
  @BeforeUpdate()
  generateAvatar() {
    this.avatar = `https://robohash.org/${this.username}`;
  }
}
What happens?
When you do:
await userRepository.save(user);

avatar = https://robohash.org/naeem

For an existing user:

@BeforeUpdate()
   ↓
generateAvatar()
   ↓
UPDATE users
But there is an important difference

Mongoose:
pre('save')
is a middleware hook.

TypeORM:
@BeforeInsert()

are entity lifecycle hooks/listeners.

For more complex logic, use a TypeORM subscriber:
@EventSubscriber()
export class UserSubscriber

  listenTo() {
    return User;

    event.entity.avatar =
      `https://robohash.org/${event.entity.username}`;
  }
}
Use a subscriber when the logic is more complicated or you want to keep the Entity clean.

Yes. The key is understanding that HTTP and GraphQL have different error models.
1. NestJS HTTP exception
When you write:

throw new ConflictException('Email or username already exists');
ConflictException is an HTTP-oriented exception.

It represents:
HTTP 409 Conflict

This makes perfect sense in a REST API:

POST /users
        ↓
duplicate email
        ↓
HTTP 409

The response might be:
{
  "statusCode": 409,
  "message": "Email or username already exists"
}


2. GraphQL works differently
GraphQL normally returns one HTTP endpoint:

POST /graphql
Even if your GraphQL operation has a business error, the HTTP request itself can still be successfully processed.
GraphQL puts the error inside the GraphQL response:
{
  "errors": [
    {
      "message": "Email or username already exists",
      "extensions": {
        "code": "CONFLICT"
      }
    }
  ],
  "data": null
}

So:

HTTP
└── status code → 200
    GraphQL
    └── errors[].extensions.code → CONFLICT

That's the fundamental difference.
How GraphQLError works

You write:

import { GraphQLError } from 'graphql';

throw new GraphQLError(
  'Email or username already exists',
  {
    extensions: {
      code: 'CONFLICT',
    },
  },
);

GraphQLError is an error class from the GraphQL library.
The important part is:

extensions: {
  code: 'CONFLICT',
}

You're adding metadata to the GraphQL error.
Apollo then sends that information to the client:

{
  "errors": [
    {
      "message": "Email or username already exists",
      "extensions": {
        "code": "CONFLICT"
      }
    }
  ]
}
Why did your ConflictException become INTERNAL_SERVER_ERROR?

You had:

throw new ConflictException(
  'Email or username already exists',
);

NestJS knows:

ConflictException
       ↓
HTTP 409

But Apollo doesn't treat NestJS's ConflictException as one of its GraphQL error codes.
So Apollo saw an unrecognized exception and produced:

"extensions": {
  "code": "INTERNAL_SERVER_ERROR"
}

Even though the underlying exception contained:
"statusCode": 409

That's why your previous response had both:

code: INTERNAL_SERVER_ERROR
status: 409

Can you use HTTP exceptions with GraphQL?

Yes, absolutely.
NestJS allows you to use:
BadRequestException
UnauthorizedException
ForbiddenException
NotFoundException
ConflictException

inside GraphQL resolvers/services.
They won't crash the application.

The question is how you want your GraphQL API to expose those errors.

Option 1 — NestJS exceptions
throw new ConflictException('Email already exists');

Simple and familiar if you're already using NestJS.

Option 2 — GraphQL errors
throw new GraphQLError('Email already exists', {
  extensions: {
    code: 'CONFLICT',
  },
});

More naturally aligned with GraphQL's error model.

One important correction
You don't necessarily need to replace every NestJS exception with GraphQLError.

For example, your validation:
new ValidationPipe()

is already producing a BadRequestException, and NestJS/GraphQL is handling that for you.

So you can choose a consistent strategy rather than thinking:
"HTTP exceptions cannot be used in GraphQL."

They can be used. It's just that GraphQL has its own error-response format.

user: User;

This means:
In JavaScript/TypeScript, I access the related user through member.user.

Example:

member.user
member.user.id
member.user.name

2. @JoinColumn is a TypeORM decorator
@JoinColumn({ name: 'user_id' })

It tells TypeORM:
The foreign-key column in the database is called user_id.

So:

TypeScript                  Database
-----------                 --------
member.user       ────────> user_id
     │                         │
   User entity              FK column



In your entity
@ManyToOne(() => UserEntity)
@JoinColumn({ name: 'user_id' })
user: Relation<UserEntity>;

You access:

member.user

not:
member.user_id
And normally you don't access member.user_id unless you explicitly define user_id as a separate column/property.

user_id is available in the database,
 but TypeORM does not automatically make every database column a property on your TypeScript entity.

Think of it as two separate layers:

DATABASE                         TYPESCRIPT ENTITY

workspace_members
┌──────────────┐                ┌────────────────────┐
│ id           │                │ id                 │
│ user_id      │ ────────────── │ user               │
│ workspace_id │                │ workspace           │
│ role         │                │ role               │
└──────────────┘  
              └────────────────────┘
Simple rule
user = property you use in TypeScript
@JoinColumn = tells TypeORM how that property maps to the database FK column.

Why can't you do this?
member.user_id

Because your TypeScript class does not have a property called user_id.

You only declared:

user: Relation<UserEntity>;

TypeScript only knows about properties you declare on the class.

If you WANT member.user_id
You can explicitly map it:

@Column({ name: 'user_id' })
userId: number;

@ManyToOne(() => UserEntity)
@JoinColumn({ name: 'user_id' })
user: Relation<UserEntity>;

Now you have:

member.userId       // FK value: 5
member.user         // UserEntity
member.user.id      // User's ID: 5

Notice I used userId, not user_id, because that's the normal TypeScript naming style.

Important distinction
member.userId
→ directly gets the FK value.

member.user
→ gets the related UserEntity when the relation is loaded.

member.user.id
→ gets the user's ID through the relation, but only if user was loaded.

So database column ≠ automatically available TypeScript property. @JoinColumn({ name: 'user_id' }) 
maps the database column to the user relation; it doesn't declare a user_id property.

# CVA (Class Variance Authority)

## 1. What is CVA?

CVA stands for Class Variance Authority.

It is a JavaScript library used to manage CSS classes based on different variants or options.

For example, a button can have different styles:
- Primary
- Secondary
- Danger
- Outline

CVA helps us define these styles in one place and select them using props.

## 2. Installation

```bash
npm install class-variance-authority
```

## 3. Basic Syntax

```jsx
import { cva } from "class-variance-authority";

const buttonVariants = cva(
  "px-4 py-2 rounded-md font-medium",
  {
    variants: {
      variant: {
        primary: "bg-blue-600 text-white",
        secondary: "bg-gray-200 text-black",
        danger: "bg-red-600 text-white",
      },
      size: {
        small: "text-sm",
        large: "text-lg",
      },
    },

    defaultVariants: {
      variant: "primary",
      size: "small",
    },
  }
);
```

## 4. Understanding Each Part

### A. Base Classes

```jsx
cva("px-4 py-2 rounded-md font-medium", ...)
```

These classes are applied to every button, regardless of its variant or size.

### B. Variants

```jsx
variants: {
  variant: {
    primary: "bg-blue-600 text-white",
    secondary: "bg-gray-200 text-black",
  },
}
```

`variants` defines the available styling options.

Here:
- `variant` is the name of the variant group.
- `primary` and `secondary` are the available options.
- The strings contain the CSS classes for each option.

### C. Multiple Variant Groups

```jsx
variants: {
  variant: {
    primary: "bg-blue-600 text-white",
    danger: "bg-red-600 text-white",
  },
  size: {
    small: "text-sm px-2 py-1",
    large: "text-lg px-6 py-3",
  },
}
```

We can define multiple independent variant groups, such as `variant` and `size`.

### D. Default Variants

```jsx
defaultVariants: {
  variant: "primary",
  size: "small",
}
```

These options are used when the caller does not provide a value for those variants.

## 5. How to Use CVA

CVA returns a function that generates class names.

```jsx
buttonVariants({
  variant: "primary",
  size: "large",
});
```

The result contains the base classes plus the selected primary and large classes.

For example:

```jsx
<button
  className={buttonVariants({
    variant: "primary",
    size: "large",
  })}
>
  Submit
</button>
```

Output: a blue button with white text and large text sizing.

## 6. Complete React Example

```jsx
import { cva } from "class-variance-authority";

const buttonVariants = cva(
  "rounded-md font-medium",
  {
    variants: {
      variant: {
        primary: "bg-blue-600 text-white",
        secondary: "bg-gray-200 text-black",
        danger: "bg-red-600 text-white",
      },
      size: {
        small: "px-2 py-1 text-sm",
        medium: "px-4 py-2 text-base",
        large: "px-6 py-3 text-lg",
      },
    },
    defaultVariants: {
      variant: "primary",
      size: "medium",
    },
  }
);

function Button({
  variant,
  size,
  children,
}) {
  return (
    <button
      className={buttonVariants({ variant, size })}
    >
      {children}
    </button>
  );
}

export default function App() {
  return (
    <div className="flex gap-3">
      <Button variant="primary" size="medium">
        Save
      </Button>

      <Button variant="secondary" size="small">
        Cancel
      </Button>

      <Button variant="danger" size="large">
        Delete
      </Button>
    </div>
  );
}
```

## 7. What Happens Internally?

When we call:

```jsx
buttonVariants({
  variant: "danger",
  size: "large",
});
```

CVA performs these steps:

1. Reads the base classes.
2. Finds the classes associated with `variant: "danger"`.
3. Finds the classes associated with `size: "large"`.
4. Combines all the applicable classes into a class-name string.
5. Returns the string for use in `className`.

## 8. What Is `compoundVariants`?

`compoundVariants` applies additional classes when multiple variant conditions match.

Example:

```jsx
const buttonVariants = cva("rounded-md", {
  variants: {
    variant: {
      primary: "bg-blue-600",
      danger: "bg-red-600",
    },
    size: {
      small: "text-sm",
      large: "text-lg",
    },
  },

  compoundVariants: [
    {
      variant: "primary",
      size: "large",
      className: "font-bold",
    },
  ],
});
```

Here, `font-bold` is applied only when both conditions are true:

```jsx
buttonVariants({
  variant: "primary",
  size: "large",
});
```

## 9. What Is `className` for?

You can pass additional classes when generating variants:

```jsx
buttonVariants({
  variant: "primary",
  size: "large",
  className: "w-full",
});
```

The `w-full` class is added to the generated classes.

## 10. What Is the Difference Between CVA and `cn()`?

- `cva()` defines reusable styling rules and variants.
- The function returned by `cva()` generates classes for the selected variants.
- `cn()` is a separate utility commonly used to combine classes and, depending on its implementation, resolve conflicting Tailwind classes.

Example:

```jsx
import { cva } from "class-variance-authority";
import { cn } from "@/lib/utils";

const buttonVariants = cva("rounded-md", {
  variants: {
    variant: {
      primary: "bg-blue-600 text-white",
      secondary: "bg-gray-200 text-black",
    },
  },
});

<button
  className={cn(
    buttonVariants({ variant: "primary" }),
    "w-full"
  )}
>
  Save
</button>
```

## 11. Important Points to Remember

1. CVA stands for Class Variance Authority.
2. CVA does not create React components; it generates class names.
3. Base classes apply to every variant.
4. `variants` defines available styling choices.
5. `defaultVariants` specifies default choices.
6. `compoundVariants` handles combinations of variant conditions.
7. CVA works with Tailwind CSS, regular CSS class names, and other class-name systems.
8. CVA does not automatically merge conflicting Tailwind classes; a utility such as `tailwind-merge` can help.
9. CVA can also be used outside React because it is a JavaScript library.

**One-line summary:** CVA lets us define reusable CSS styles once and dynamically select the appropriate classes through options such as `variant` and `size`.

```js
const container = containerRef.current;

const editorContainer = container.appendChild(
  container.ownerDocument.createElement('div')
```

**1. `containerRef.current`**
Gets the actual DOM element stored in the React ref.

**2. `container.ownerDocument`**
Gets the document (`document`) that owns the container element.

**3. `createElement('div')`**
Creates a new, empty `<div>` element.

**4. `appendChild()`**
Adds the newly created div inside the container.

**5. `editorContainer`**
Stores the newly created div that was appended to the container not the container.

**Example:**

Before:
```html
<div id="container"></div>
```

After:
```html
<div id="container">
  <div></div>
</div>
```

**In short:** Get the container → create a div → append it inside the container → store the new div for Quill.

Why not just use document.createElement('div')?
You can! For a normal webpage, both usually work the same way.
container.ownerDocument is useful when your container belongs to another document, such as an iframe.
Remember: ownerDocument finds the document; it does not create a div or append anything by itself.

  orderId: string,
  paymentId: string,
  signature: string,
) {
  const generatedSignature = crypto
    .createHmac(
      'sha256',
      process.env.RAZORPAY_KEY_SECRET!,
    )
    .update(`${orderId}|${paymentId}`)
    .digest('hex');

  return generatedSignature === signature;
}

Add a verification endpoint to your controller:
@Post('verify')
verifyPayment(
  @Body()
  body: {
    razorpay_order_id: string;
    razorpay_payment_id: string;
    razorpay_signature: string;
  },
) {
  return {
    verified: this.razorpayService.verifyPayment(
      body.razorpay_order_id,
      body.razorpay_payment_id,
      body.razorpay_signature,
    ),
  };
}

Then call this endpoint from React inside the Checkout handler.
