Option 1 — @BeforeInsert() / @BeforeUpdate() ⭐
For your case, this is the simplest approach.

import {
  Entity,
  PrimaryGeneratedColumn,
  Column,
  BeforeInsert,
  BeforeUpdate,
} from 'typeorm';

@Entity('users')
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ unique: true })
  email: string;

  @Column()
  password: string;

  @Column({ unique: true })
  username: string;

  @Column({ nullable: true })
  avatar: string;

  @BeforeInsert()
  @BeforeUpdate()
  generateAvatar() {
    this.avatar = `https://robohash.org/${this.username}`;
  }
}
What happens?
When you do:
await userRepository.save(user);

avatar = https://robohash.org/naeem

For an existing user:

@BeforeUpdate()
   ↓
generateAvatar()
   ↓
UPDATE users
But there is an important difference

Mongoose:
pre('save')
is a middleware hook.

TypeORM:
@BeforeInsert()

are entity lifecycle hooks/listeners.

For more complex logic, use a TypeORM subscriber:
@EventSubscriber()
export class UserSubscriber

  listenTo() {
    return User;

    event.entity.avatar =
      `https://robohash.org/${event.entity.username}`;
  }
}
Use a subscriber when the logic is more complicated or you want to keep the Entity clean.

Yes. The key is understanding that HTTP and GraphQL have different error models.
1. NestJS HTTP exception
When you write:

throw new ConflictException('Email or username already exists');
ConflictException is an HTTP-oriented exception.

It represents:
HTTP 409 Conflict

This makes perfect sense in a REST API:

POST /users
        ↓
duplicate email
        ↓
HTTP 409

The response might be:
{
  "statusCode": 409,
  "message": "Email or username already exists"
}


2. GraphQL works differently
GraphQL normally returns one HTTP endpoint:

POST /graphql
Even if your GraphQL operation has a business error, the HTTP request itself can still be successfully processed.
GraphQL puts the error inside the GraphQL response:
{
  "errors": [
    {
      "message": "Email or username already exists",
      "extensions": {
        "code": "CONFLICT"
      }
    }
  ],
  "data": null
}

So:

HTTP
└── status code → 200
    GraphQL
    └── errors[].extensions.code → CONFLICT

That's the fundamental difference.
How GraphQLError works

You write:

import { GraphQLError } from 'graphql';

throw new GraphQLError(
  'Email or username already exists',
  {
    extensions: {
      code: 'CONFLICT',
    },
  },
);

GraphQLError is an error class from the GraphQL library.
The important part is:

extensions: {
  code: 'CONFLICT',
}

You're adding metadata to the GraphQL error.
Apollo then sends that information to the client:

{
  "errors": [
    {
      "message": "Email or username already exists",
      "extensions": {
        "code": "CONFLICT"
      }
    }
  ]
}
Why did your ConflictException become INTERNAL_SERVER_ERROR?

You had:

throw new ConflictException(
  'Email or username already exists',
);

NestJS knows:

ConflictException
       ↓
HTTP 409

But Apollo doesn't treat NestJS's ConflictException as one of its GraphQL error codes.
So Apollo saw an unrecognized exception and produced:

"extensions": {
  "code": "INTERNAL_SERVER_ERROR"
}

Even though the underlying exception contained:
"statusCode": 409

That's why your previous response had both:

code: INTERNAL_SERVER_ERROR
status: 409

Can you use HTTP exceptions with GraphQL?

Yes, absolutely.
NestJS allows you to use:
BadRequestException
UnauthorizedException
ForbiddenException
NotFoundException
ConflictException

inside GraphQL resolvers/services.
They won't crash the application.

The question is how you want your GraphQL API to expose those errors.

Option 1 — NestJS exceptions
throw new ConflictException('Email already exists');

Simple and familiar if you're already using NestJS.

Option 2 — GraphQL errors
throw new GraphQLError('Email already exists', {
  extensions: {
    code: 'CONFLICT',
  },
});

More naturally aligned with GraphQL's error model.

One important correction
You don't necessarily need to replace every NestJS exception with GraphQLError.

For example, your validation:
new ValidationPipe()

is already producing a BadRequestException, and NestJS/GraphQL is handling that for you.

So you can choose a consistent strategy rather than thinking:
"HTTP exceptions cannot be used in GraphQL."

They can be used. It's just that GraphQL has its own error-response format.

user: User;

This means:
In JavaScript/TypeScript, I access the related user through member.user.

Example:

member.user
member.user.id
member.user.name

2. @JoinColumn is a TypeORM decorator
@JoinColumn({ name: 'user_id' })

It tells TypeORM:
The foreign-key column in the database is called user_id.

So:

TypeScript                  Database
-----------                 --------
member.user       ────────> user_id
     │                         │
   User entity              FK column



In your entity
@ManyToOne(() => UserEntity)
@JoinColumn({ name: 'user_id' })
user: Relation<UserEntity>;

You access:

member.user

not:
member.user_id
And normally you don't access member.user_id unless you explicitly define user_id as a separate column/property.

user_id is available in the database,
 but TypeORM does not automatically make every database column a property on your TypeScript entity.

Think of it as two separate layers:

DATABASE                         TYPESCRIPT ENTITY

workspace_members
┌──────────────┐                ┌────────────────────┐
│ id           │                │ id                 │
│ user_id      │ ────────────── │ user               │
│ workspace_id │                │ workspace           │
│ role         │                │ role               │
└──────────────┘  
              └────────────────────┘
Simple rule
user = property you use in TypeScript
@JoinColumn = tells TypeORM how that property maps to the database FK column.

Why can't you do this?
member.user_id

Because your TypeScript class does not have a property called user_id.

You only declared:

user: Relation<UserEntity>;

TypeScript only knows about properties you declare on the class.

If you WANT member.user_id
You can explicitly map it:

@Column({ name: 'user_id' })
userId: number;

@ManyToOne(() => UserEntity)
@JoinColumn({ name: 'user_id' })
user: Relation<UserEntity>;

Now you have:

member.userId       // FK value: 5
member.user         // UserEntity
member.user.id      // User's ID: 5

Notice I used userId, not user_id, because that's the normal TypeScript naming style.

Important distinction
member.userId
→ directly gets the FK value.

member.user
→ gets the related UserEntity when the relation is loaded.

member.user.id
→ gets the user's ID through the relation, but only if user was loaded.

So database column ≠ automatically available TypeScript property. @JoinColumn({ name: 'user_id' }) 
maps the database column to the user relation; it doesn't declare a user_id property.

import {

| Operator            | Example                      | SQL meaning             |
| ------------------- | ---------------------------- | ----------------------- |
| `In()`              | `id: In([1, 2, 3])`          | `IN (1,2,3)`            |
| `Not()`             | `id: Not(5)`                 | `!= 5`                  |
| `MoreThan()`        | `id: MoreThan(5)`            | `> 5`                   |
| `MoreThanOrEqual()` | `id: MoreThanOrEqual(5)`     | `>= 5`                  |
| `LessThan()`        | `id: LessThan(5)`            | `< 5`                   |
| `LessThanOrEqual()` | `id: LessThanOrEqual(5)`     | `<= 5`                  |
| `Between()`         | `id: Between(5, 10)`         | `BETWEEN 5 AND 10`      |
| `Like()`            | `name: Like('%test%')`       | `LIKE '%test%'`         |
| `ILike()`           | `name: ILike('%test%')`      | case-insensitive `LIKE` |
| `IsNull()`          | `description: IsNull()`      | `IS NULL`               |
| `IsNotNull()`       | `description: Not(IsNull())` | `IS NOT NULL`           |

Rule for writing good code.

### Frontend API Architecture

1. **API Folder**

   * Create an `api` folder for all REST APIs and GraphQL operations.
   * **REST:** Make the API call and return the response.
   * **GraphQL:** Write the required queries and mutations using `gql`.

2. **Hooks**

   * Create custom hooks for calling the APIs.
   * Use the appropriate query/mutation library.
   * The hook should return:

     * `data`
     * `loading`
     * `error`
     * `mutate` function for performing operations

3. **Page / Component**

   * Use the custom hook in the respective page or component.
   * Use the returned `data`, `loading`, `error`, and `mutate` function to implement the required functionality and UI behavior.

### Flow

**API → Hook → Page/Component**

* `api` → Handles API communication.
* `hook` → Handles API state and exposes the required functions/data.
* `page/component` → Uses that data and functions to implement the actual functionality.
